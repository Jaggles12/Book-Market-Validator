2. So what’s really the problem?

To answer your questions directly:

Are we relying too much on our code and not enough on an LLM in order to identify the genre on the front end?

Yes.

You’re using the LLM in step 1 (niche extraction), but then:

Genre inference is mostly heuristic: “pick the most common / strongest Amazon category path among enriched books.”

Your “anchor check” is too loose: the only invalidCategories are Fiction and Romance, so any nonfiction category – including highly specific cultural ones – passes.

The hard-locked UI genre (nonfiction) isn’t being enforced strongly enough: you still allow a Children’s eBook path to become primary.

Or are we having problems with the data returned by rainforest?

Rainforest data here is fine and pretty typical:

It returns multiple category paths per book.

Some of them are kids’ sleep, some are self-help, one is Black & African American, etc.

The problem is not the data; it’s how your code chooses which path “wins” and how little that is constrained by the original user intent.

3. Why I can “see” the mismatch and your app cannot

In this chat, I’m effectively doing a “meta validation” step:

I see:

Your production pipeline doesn’t have this step.

Output → final genre + verdict.

You don’t do:

That missing last step is where the disconnect lives.

4. Concrete suggestions based on this output

Here’s how I’d fix this without ripping your architecture apart:

4.1. Treat user intent + UI genre as hard constraints

Add simple, explicit rules in your genre inference code:

No race/ethnicity inference unless user said so.

If a category path contains “Black & African American”, “Latino”, “Asian”, etc. and the user did not indicate a cultural focus:

Do not use that as primary genre.

At most, mark it as a possible sub-niche or “optional angle”.

Nonfiction lock means:

Don’t make any Children’s eBook / Picture Book path the primary genre.

If you must straddle, keep the primary genre in a nonfiction parenting / self-help path (e.g. Parenting, Family Health, Child Development) and mention the children’s categories as secondary shelves.

For this run, a sane genre result would have been something like:

Primary: Parenting / Sleep / Emotional Regulation (nonfiction)

Secondary shelves: Children’s Sleep, Kids’ Emotional Literacy

Note: Some comps are in Black & African American subcategories; you could niche there if you choose.

4.2. Add a final LLM “sanity check” step

Call the LLM again at the end with a prompt like (pseudo):

System: You are a publishing strategist…
User:

Original idea: "..."

Audience profile: {...}

UI-selected genre: "nonfiction / general nonfiction"

Canonical niche anchor: "Parenting & Family"

Candidate final genre: {genre object you computed}

Book sample (titles, category paths, ranks, semantic buckets)

Stats: {coreStats, adjacentStats, marketSignal}

Questions:

Does the candidate final genre match the original idea and anchor, or is it drifting?

If drifting, propose a corrected primary genre label and category path.

Given the stats, should the verdict be GREEN (strong), YELLOW (promising but thin), or RED (weak)? Explain briefly.

Then you:

Use the LLM’s corrected genre as your final.

Use its verdict recommendation instead of hard-coded Green messaging when the data is thin.

That’s basically what I’m doing in my head when I review your JSON.

4.3. Tighten your category weighting & purity logic

From your logs:

categoryPurity: '0.000'
...
✅ Genre alignment OK: purity score 0.50


This suggests:

You first detect low purity → niche is noisy.

Then some later step or threshold relaxes and suddenly claims 0.50 is enough to say “alignment OK”.

I’d change that:

If initial categoryPurity < 0.4 and coreBookCount < 5, mark the genre as “uncertain” and:

Don’t pick a hyper-specific microcategory (like Black & African American) as primary.

Default to the broader anchor (“Parenting & Family”) and let the LLM describe that the comps are scattered across children’s sleep, journals, etc.

4.4. Upgrade your GREEN/YELLOW/RED logic

In this run:

coreStats:

avgReviews: 17.5

all low-review books

bsrBuckets: { veryStrong: 1, moderate: 1, weak: 1 }

marketSignal: "signalStrength": "moderate"

Yet you output:

I would add guardrails like:

If coreStats.totalBooks < 5 → never GREEN. Cap at YELLOW.

If coreStats.lowReviewBooks / coreStats.totalBooks > 0.66 → treat as “lightly validated”.

Let the LLM see these flags and choose phrasing like:

“Promising but lightly validated niche with room to pioneer”
instead of “solid, proven demand.”

5. Answering your “why” in one sentence

The mismatch exists because your current pipeline uses the LLM to start the niche definition, then lets your own heuristics — driven heavily by a single outlier Amazon category path — override the original intent, and you never bring the LLM back in at the end to sanity-check the final genre and verdict against what the author actually asked for.

If you:

Treat the user’s intent + UI genre as true anchors,

Add a “no race/ethnicity inference unless requested” rule, and

Add a final LLM reconciliation step over your computed genre + stats,

you’ll catch exactly the kind of misalignment I just flagged, on the front end, before the author ever sees the wrong niche.
